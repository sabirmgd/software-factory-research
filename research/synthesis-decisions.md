# Synthesis decisions

These are proposed defaults for our model, not claims that the sources prescribe one unified workflow. Each decision has a reason and a condition for revision.

| ID | Proposed decision | Why | Revisit when |
| --- | --- | --- | --- |
| D01 | Optimize sustainable customer outcomes, not generated code | Software is an intervention, not the final objective | The outcome definition is not observable or is outside the project's influence |
| D02 | Use three feedback loops | Delivery alone cannot evaluate value or reduce recurring effort | The separation creates duplicated ownership rather than clearer decisions |
| D03 | Scale planning with uncertainty and risk | Preserve useful review points without ritual documents | Routing misses consequential surprises or consumes excessive attention |
| D04 | Keep product and technical decisions identifiable | Prevent implementation from silently inventing behavior | Small work can combine the artifacts without losing clarity |
| D05 | Design public usage and ownership before private detail | Give agents a bounded view that supports correct change | Real requirements repeatedly contradict the chosen interface |
| D06 | Enforce a few high-confidence constraints | Reduce recurring mistakes without relying only on memory | False positives or legitimate exceptions dominate |
| D07 | Preauthorize implementation, not changes to authority | Preserve autonomy while keeping consequential decisions accountable | Evidence shows the boundaries are too vague or unnecessarily restrictive |
| D08 | Make Clear serves understanding, not mandatory approval | Reduce reconstruction and support exploration | Visuals increase confidence without improving comprehension |
| D09 | Keep evidence separate from the author's claims | Make success inspectable and prevent silent weakening of criteria | Evidence collection costs exceed value for a demonstrably low-risk task |
| D10 | Separate release authority from design approval | Side effects and recovery differ by environment | A specific low-risk deployment class has been explicitly preauthorized |
| D11 | Limit unfinished work according to the actual constraint | More active agents do not necessarily mean more completed outcomes | Measured flow shows a different constraint or limit is appropriate |
| D12 | Promote reusable patterns selectively | Avoid spreading project-specific assumptions | A capability has demonstrated repeated value across appropriate contexts |
| D13 | Preserve rule retirement | Prevent the factory from becoming accumulated bureaucracy | A retired rule's failure class recurs and needs a revised mechanism |
| D14 | Keep this publication separate from the application starter | Distinguish research from executable product defaults | A small runnable example materially improves understanding |

## Explicit departures from source defaults

PStack's architect checkpoint is opt-in in the inspected source. Our client-work proposal requires explicit authority for consequential boundary changes. RPI offers separate reviews and flexible routes; our compact path can combine artifacts when the decisions are already settled. Make Clear is our broader understanding capability, not a claim that the inspected `show-me` skill implements every proposed behavior.

## Decisions still belonging to the author or project

The eventual application's ORM, identity provider, deployment target, package manager, exact versions, tenancy semantics, and security roles remain unapproved choices. The original publication's blanket reuse license is also not selected. The repository does not silently convert suggested defaults into approved commitments.
