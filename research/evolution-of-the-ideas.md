# How the ideas changed

This is an editorial reconstruction of the visible discussion's intellectual development, not a timestamped transcript. Each change preserves why the later position differs from the earlier one.

## From code generation to sustainable change

The starting interest was agent-driven software development. Verification and maintenance quickly emerged as work that faster generation did not remove. The goal widened to more reliable client outcomes without proportional supervision and future support burden. The remaining question is whether our mechanisms improve that whole system rather than only implementation speed.

## From architecture once to stable defaults with revision

The initial leverage intuition was to spend an hour on foundations so many later tasks benefit. The correction was that architecture cannot be frozen against new evidence. We now distinguish stable contracts from permanent guesses. Consequential changes require explicit revision; private implementation detail can evolve within them.

## From complete planning to adaptive planning

PRD, technical design, and outline clarified different decisions. The risk was turning useful distinctions into mandatory paperwork. We retained the information ownership but made artifact depth depend on uncertainty, risk, and what is already settled. A small change can use one brief; a new sharing policy cannot be treated as trivial merely because its code is short.

## From implicit program structure to caller-first design

The discussion exposed how high-level architecture can coexist with messy internals. Program design became a place to inspect public interfaces, ownership, types, and call sequences. Poteto's architect skill added structural alternatives and caller-first sketches. We adopted the mechanism without making exhaustive alternatives mandatory for every small edit.

## From reminders to executable constraints

Repeated instructions about permissions and imports seemed too fragile. The model moved toward typed registries, route inventories, runtime checks, dependency rules, and tested generators. The qualification is that enforcement proves conformance to a rule, not that the rule is wise or complete.

## From autonomy as an agent quality to a task contract

The desired balance was initially described as agents executing while humans decide important things. That required a concrete trigger. We introduced approved scope, explicit authority, evidence requirements, recovery limits, and stop conditions. The remaining calibration problem is how to classify work without requiring a new human decision for every task.

## From visual approval to human understanding

Make Clear began with dissatisfaction with text-only review. The broader insight was that understanding may be the entire goal: learning a system, exploring a possibility, or challenging an assumption need not end in approval. The capability chooses the smallest useful representation and preserves uncertainty. Its effect on actual comprehension remains to be tested.

## From passing tests to claims with evidence

A verification loop is useful only when its checks correspond to accepted behavior and cannot be weakened invisibly. We distinguished local checks, independent review, runtime evidence, and release authority. A test report now carries a revision and limitations rather than a broad declaration that the system works.

## From more agent activity to flow through the constraint

If the human or client decision is the bottleneck, more concurrent implementation can increase unfinished work. The model therefore includes WIP and waiting states. The factory may improve evidence or finish existing work rather than start another feature simply to keep an agent busy.

## From project learning to selective factory learning

A recurring correction can become an asset: a better interface, a check, a generator, or shared language. But every incident should not become a permanent rule. We added the ability to delete obsolete constraints and separate reusable foundations from project-specific policies and experiments.

## From shipped to outcome evaluated

The final widening recognized that software is a means. Acceptance, deployment, adoption, and customer benefit are different states. The customer-value loop can change priorities or recommend a non-software intervention. This is the deepest change in the objective of the factory.
